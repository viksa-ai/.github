# Application modernization evidence

This record defines what the application modernization proves and, equally
importantly, what it does not prove. It is intended to be read with the
machine-readable report produced by `scripts/verify_backend_architecture.py`.

## Scope and safety boundary

The completed work is source-code and local verification work across the 15
Python backend repositories, `ui-service`, and the shared
`viksa-platform-runtime` package. It does not mutate Kubernetes, GKE, cloud
resources, production databases, production quotas, live secrets, HMAC keys,
or customer data. No production load or chaos traffic is generated by these
gates.

The following remain separate operator-controlled release activities:

- publish and attest `viksa-platform-runtime==0.2.0` before service images are
  built from registry-only requirements;
- execute reviewed database migrations and reconciliation plans against a
  named production target;
- rotate HMAC and other secrets using receiver-first rollout evidence;
- run inventory reconciliation and downstream deletion workers against live
  records;
- validate HA, autoscaling, NetworkPolicy, workload identity, regional
  recovery, and load/chaos behavior in the intended production environment.

## Backend architecture acceptance contract

Every backend is evaluated against the same canonical package structure:

```text
src/<service_package>/
  domain/
  application/
  ports/
  infrastructure/
  entrypoints/
  bootstrap/
```

The verifier enforces all of the following without service-specific waivers:

- all canonical layers exist;
- domain code is framework-free and dependencies point inward;
- application and port code do not import concrete adapters;
- resource construction and concrete dependency wiring occur only in the
  bootstrap composition root;
- historical modules are import-only identity-preserving facades;
- strict Mypy configuration covers production modules and cannot suppress
  imported application code;
- canonical and historical production trees contain no meaningful exact
  function or file copies, within or between repositories.

Run the authoritative fleet gate from `.github`:

```bash
python3 scripts/verify_backend_architecture.py \
  --workspace /Users/flagship \
  --contract quality/backend-architecture-contract.json \
  --json-out /private/tmp/backend-architecture-final.json
```

The verifier exits non-zero if any repository or any of its four duplication
arrays fails. Its own regression suite is:

```bash
python -m pytest -q tests/test_verify_backend_architecture.py
```

## Shared runtime and migration strategy

Cross-service behavior is owned by the typed `viksa-platform-runtime` package,
including authentication helpers, tenant and internal-request security,
logging, metrics, tracing, Redis/TLS configuration, Mongo helpers, usage-limit
parsing, lifecycle primitives, and compatibility module aliasing. Service code
retains business-specific policy and adapts shared behavior at bootstrap or
infrastructure boundaries.

Historical import paths remain stable through module-identity aliases during
the migration. This preserves imports, monkeypatch targets, singleton caches,
and exception/class identity while removing the old implementation copies.
Identity regression tests accompany migrated services.

Local builds use the workspace package source. A production release must not
assume the package already exists in an external registry: publish and attest
version `0.2.0`, then rebuild every consuming service from the immutable
artifact before deployment.

## Application safety capabilities

### HMAC rotation and workload callers

Internal requests use exact method/path/body signing, timestamp and replay
validation, constant-time verification, and current/previous key rings. Auth's
authorization policy inventories every protected method/path separately and
grants only the workloads that use that operation; unknown methods, paths,
wildcards, and correctly signed cross-route callers fail closed. Receivers can
accept the new and previous keys during a bounded receiver-first rotation while
signers emit the active key. Exhaustive policy tests cover every configured
positive and negative caller/route pair, in addition to missing, weak,
malformed, stale, unknown-caller, and false-validation inputs.

This proves the application protocol and rollout compatibility. It does not
rotate a live secret or prove a deployed workload-identity binding.

### Quota reconciliation

Auth owns framework-free quota reconciliation policy and ports. Builder,
Devspace, and Scheduler persist operation identities and explicit quota states
before or around remote effects, use atomic claims/leases for recovery, avoid
double reservation/release, and quarantine legacy-unknown records for reviewed
reconciliation rather than guessing.

This proves deterministic state transitions, replay safety, and crash recovery
in tests. It does not classify or change historical production records.

### Durable deletion and downstream cleanup

Builder, Devspace, and Scheduler persist lifecycle operation identities and
quota/deletion states around remote effects. Directory Sync and Headless use
durable cleanup inboxes/outboxes with bounded inventory recovery. Marketplace
persists a tenant-bound installation-cleanup ledger and now independently scans
tenant databases for failed or expired operations with a hard per-pass bound,
per-tenant failure isolation, and a fair in-process scan cursor; atomic claims
fence multiple replicas. Workflow now persists deletion intent before cleanup,
discovers pending work through a bounded account inventory, isolates failures
by account and item, checkpoints capped retries, and owns its periodic worker
through application lifespan DI.

Stable operation identities, expiring leases, retryable states, idempotent
downstream calls, and completion markers allow abandoned work to resume. Hard
deletion is ordered after required downstream and quota effects. A malformed
or cross-tenant recovery document fails closed rather than deleting by
inference.

This proves application behavior under tested retries, crashes, duplicate
delivery, stale leases, and partial downstream failure. It does not execute a
live deletion or prove every external provider's production behavior.
Marketplace and Workflow currently derive inventory from non-system Mongo
database names because no authoritative account-catalog port is available;
that adapter is replaceable when such a catalog exists. Marketplace's fair
scan cursor resets after process restart, and its cleanup operation has no
lease heartbeat, per-operation timeout, or poison-item quarantine, so a hung
provider can stall one pass and work that exceeds the lease can be reclaimed.
An upstream command that never reached Marketplace remains the Builder
outbox's responsibility.

### Recovery and resource lifecycle

HTTP/Redis/Mongo clients use bounded timeouts and managed async lifecycles;
startup/readiness and shutdown paths own their resources through bootstrap DI.
Background recovery workers have bounded batches, ownership fencing, backoff,
and observable outcomes. Package smoke tests verify that canonical wheels do
not rely on repository-root compatibility modules.

Trace's reconciliation daemon now has direct tests for inventory failure,
per-account isolation, stale-span repair, bounded pass arguments, retry after a
pass failure, and cancellation. Its repairs are idempotent, but it currently
has no distributed pass lease, persisted pass checkpoint, or per-account
timeout; duplicate work across replicas and a sequential adapter stall remain
known runtime limitations.

### Migration and reconciliation tooling

Legacy Auth mongosh migrations now share one dry-run-default runtime with
explicit target/database binding, exact apply confirmation, bounded batches
and invocation budgets, ordered cursors, majority-written checkpoints, and
resume behavior. Directory's project-user migration is dry-run by default,
uses bounded keyset pages, performs no index/source writes in dry-run mode,
binds apply approval and its checkpoint to a credential-free target fingerprint
and the requested wildcard or project scope, and atomically checkpoints
completed projects under a host-local lock. It also fixes the historical
account-wide path that treated a database-name string as a database object.

Volt's account-database migration is a canonical domain/application/port
workflow with a full no-write preflight, target collision checks, bounded
source pages, insert-only idempotence, source-plan drift detection, and
target-bound, resumable local checkpoints and reports. Auth quota and encrypted
SSO/OAuth migration tools likewise expose dry-run/inventory paths for reviewed
operation.

These controls prove that the tools fail closed and can be reviewed and
resumed locally. They do not constitute execution against production. Local
checkpoint files and locks are not cross-host coordination, and Mongo cannot
provide one transaction spanning source and target databases.

## Frontend acceptance gates

`ui-service` has repository-wide strict TypeScript, ESLint accessibility,
explicit-`any`, AST inventory/accessibility, unit, production-build, and bundle
budget gates:

```bash
npm run typecheck
npm run lint
npm run lint:no-any
npm run audit:ui:check
npm run test
npm run test:e2e
npm run build
npm run budget:bundle
```

Integrated local result on 2026-08-04:

| Gate | Result |
| --- | --- |
| TypeScript / ESLint | strict typecheck and zero-warning lint passed |
| Explicit `any` inventory | 765 TypeScript files checked; zero findings |
| TSX accessibility inventory | 513 TSX files and 125 App Router routes; all configured issue budgets at zero |
| Vitest | 224 tests in 52 files passed |
| Playwright | 24 desktop/mobile Chromium tests passed |
| Next production build | 172 static pages generated successfully |
| Bundle budget | 131 routes; 141 KB median gzip, 226.8 KB p90, 332.5 KB maximum; no route above 350 KB |

The generated audit inventories every TSX file and App Router page, classifies
interactive accessible-name sources, and fails on unnamed controls,
disconnected labels, pointer-only click targets, keyboard-inaccessible rows,
missing image alternatives, positive tab indexes, hover-only actions, or stale
review allowlist entries. The bundle gate measures gzip bytes from the actual
Next build manifest rather than source-size estimates.

The Playwright gate exercises public, authentication, documentation, API
mutation, responsive-navigation, and security-header contracts in both desktop
and mobile Chromium profiles. Its mutation tests derive the Origin header from
Playwright's configured base URL so the CSRF policy is tested rather than
bypassed by a duplicated hostname constant.

Static and build gates do not replace signed-in browser, assistive-technology,
or real-user performance testing. Those require representative accounts,
data, devices, and a deployed environment and must be recorded separately.

## Performance and resilience claim boundary

The application changes improve bounded I/O, pooling, backpressure, pagination,
batching, serialization limits, idempotency, and recovery behavior. Unit and
integration tests prove those contracts at local scale. They are not evidence
of one million completed production requests, thousands of simultaneous users,
regional failover, disaster recovery, or chaos tolerance.

Those claims become valid only after target-bound reports are captured from a
representative HA environment, with immutable build identities, dataset and
traffic definitions, latency/error/resource measurements, failure scenarios,
recovery objectives, and raw result artifacts. Confirmation text alone is not
evidence.
